Selling point: durable agent memory

Graph nodes decide what matters, then retrieve it when the work rhymes.

Orange is already built around a completed-session memory loop: capture the session, triage whether it is durable, extract compact Insight nodes, write Neo4j plus Chroma, then recall similar memories before the next agent answers.

Where are we? Implemented for completed sessions, demo chat, MCP handlers, Neo4j graph writes, Chroma vector writes, user/global scoping, and recall.
What gets stored? Technical learning, root causes, tried approaches, durable user/company facts, preferences, and product steering. Generic chats are skipped.
How retrieval works? Query text is embedded through Chroma, filtered by user email and/or company org, score-gated, then hydrated from Neo4j with neighborhood context.

End-to-end loop

What happens when a conversation is marked done

The current code path is centered in core/agents/orchestrator.py, with writes in core/graph_upsert/writer.py and recall in core/mcp_server/handlers.py.

01 ingest

Normalize session

Source, messages, timestamps, profile metadata, user email, company, org id, and source URL become a NormalizedSession.

02 trigger

Only after done

The demo and MCP path call store_session after completion, so Orange stores outcomes, not every half-formed exchange.

03 triage

Worth storing?

User and global triage agents decide if there is reusable memory. Fallback regex rules keep the system working if LLM triage fails.

04 extract

Insight drafts

The extractor returns a minimal list of InsightDraft objects: what, why, how, outcome, memory_kind, tags, label, summary.

05 write

Neo4j + Chroma

Neo4j gets Session and Insight nodes plus PRODUCED and SIMILAR_TO edges. Chroma gets searchable vector documents.

06 recall

Use next time

recall_memory searches vectors, filters by scope, then hydrates matching graph nodes and neighborhoods for the agent.

Retrieval

What happens when a similar question appears later

Chroma finds semantic candidates. Neo4j turns them into useful context by fetching node details and nearby graph relationships.

1
Agent calls recall_memory(query, user_id, source, email, company, scope)

Demo chat does this before answering. MCP exposes the same tool to connected agent clients.

2
Chroma searches scoped vector collections

User memory uses orange_user_vectors filtered by user_email or user_id. Shared memory uses orange_global_vectors filtered by org_id.

3
Neo4j hydrates the winning nodes

For Insight nodes, recall returns display fields, what/why/how, tags, session summary, raw session id, and similar insight labels.

Dedup and similar-node behavior

On write, new Insight documents are compared against existing scoped vectors. If the same generated node id appears, the duplicate is skipped. If another node scores at least 0.88, Orange writes SIMILAR_TO instead of pretending it is unrelated.

Why graph plus vector is the selling point

Vector search answers "does this sound similar?" The graph answers "what exactly did we learn, who can see it, which session produced it, and what other nodes are adjacent?"

Implemented: private and shared scopes

Implemented: retrieval before demo answers

Implemented: graph inspection endpoints

The backend exposes graph, Chroma, health, and MCP routes for checking nodes and vector collection state.

Partial: full dedup semantics

Insight similarity is present with a 0.88 threshold and SIMILAR_TO edges. True semantic merging is conservative and still more mature in legacy Problem dedup.

Partial: retrieval quality ranking

Recall score-gates results and dedupes by label, preferring user memory over global duplicates. It does not yet do LLM reranking or multi-hop graph expansion beyond the fetched neighborhood.

Deep details

Exact answers you can use in a pitch

What makes the agent say "this is worth storing"?
  • The user triage prompt says to store concrete technical problems, evaluated approaches, discovered root causes, non-obvious decisions, interesting failures, durable facts, and steering feedback.
  • The global triage prompt is stricter: store only company/org facts, internal workflow constraints, durable company decisions, incidents, or technical causes useful to coworkers in the same company.
  • Fallback triage looks for durable signals such as error, failed, fixed, resolved, root cause, tried, prefer, should, steering, company uses, markdown, AWS Glue, GTM, pricing, investors, and launch strategy.
  • Low-signal patterns like hello, thanks, reverse a string, "what is Orange", or a generic create-a-website request without reusable steering are skipped.
What fields are embedded for retrieval?

The Insight embedding string is built from what, why, how, memory_kind, and tags. The display label alone is not enough, because short labels collide. This is why a later query can match the underlying situation even when it uses different wording.

What happens if someone asks a similar question already present in nodes?

recall_memory queries Chroma with the new question, filters candidates by identity and scope, converts distance to similarity, drops low scores, fetches matching nodes from Neo4j, and returns node_data plus neighborhood. The agent receives that compact memory context before producing its answer.

How are private and company memories kept apart?

User vectors require scope=user plus user_email or user_id. Global vectors require scope=global plus org_id. The global pipeline uses a user-message transcript and PII scrubber, and it refuses shared memory when no company/org context exists.

What should be improved next?
  • Add a retrieval evaluation set with known queries, expected node ids, and score thresholds.
  • Add LLM reranking after Chroma for close candidates and ambiguous queries.
  • Expose "why this was stored" and "why this was retrieved" in the UI for sales demos.
  • Make duplicate Insight handling richer: merge recurrence counts or update summaries instead of only skipping exact generated ids and linking similar nodes.
  • Add multi-hop expansion controls for related sessions, similar insights, and old Problem/Solution neighborhoods.

One-line product framing

Orange does not store chat logs. It converts completed work into scoped graph memory, then lets future agents retrieve the exact prior learning when a semantically similar situation appears.
